PART 2: TOP 10 COMMON BEGINNER MISTAKES & FIXES
================================================================================
1. Authenticating inside default() on every iteration -> Move to setup()
2. Reading files inside default() -> Use SharedArray from k6/data in init context
3. Omitting sleep() think time -> Add realistic sleep(1) pauses
4. Expecting check() to fail CI -> Define thresholds in options (exit code 99)
5. Confusing VUs with RPS -> Use constant-arrival-rate executor for strict RPS
6. Reusing hardcoded IDs -> Extract dynamic response parameters (res.json().id)
7. Importing standard Node.js packages -> Use native k6 modules or jslib.k6.io
8. Starting without ramp-up stages -> Configure gradual stages in options
9. Not tagging requests -> Add tags: { service: 'orders-api' } to isolate latencies
10. Default file descriptor limits -> Run ulimit -n 65535 on runner machines

Q1: Architecture difference between k6 and JMeter?
A: k6 is written in Go, uses goroutines (~20-40KB/VU), and modern ES6 JS. JMeter is Java JVM-based, thread-per-VU, and requires XML test plans.

Q2: What exit code does k6 return on threshold failure?
A: Non-zero POSIX status code 99, halting CI/CD pipelines.

Q3: Explain the 4 stages of k6 test lifecycle.
A: 1) Init (load SharedArray), 2) Setup (auth/seed once), 3) VU (parallel test loops), 4) Teardown (cleanup once).

Q4: Difference between check() and threshold?
A: Checks are diagnostic assertions that never halt tests; thresholds are enforceable SLAs that return exit code 99 on breach.

Q5: Why use SharedArray?
A: It loads datasets once into read-only shared memory, eliminating per-VU RAM duplication and preventing OOM crashes.

## 🧮 Topic 4: Concurrency Math: VUs vs Iterations vs Duration
**Timestamp:** [27:00 - 41:30]

### Key Formula
$$\text{Throughput (RPS)} = \frac{\text{Active VUs}}{\text{Response Time} + \text{Think Time}}$$

### Core Takeaways
1. In `shared-iterations`, total requests equal the iteration count regardless of VU speed differences.
2. In `constant-vus` with a `duration`, total requests = `(Duration / Iteration Time) * VUs`.
3. Throughput is governed by server latency plus sleep pacing.

## 🔄 Topic 5: The 4-Stage Test Life Cycle: Init, Setup, VU, Teardown
**Timestamp:** [42:00 - 50:30]

### Extracted Code: `script0.js`
```javascript
// 1. INIT STAGE (Runs once during test initialization)
import http from 'k6/http';
import { sleep } from 'k6';

export const options = {
    vus: 5,
    duration: '10s',
};

// 2. SETUP STAGE (Runs ONCE before VUs start)
export function setup() {
    console.log("=== Setup: Preparing test environment / Auth ===");
    return { authToken: "secret-token-123", testId: 999 };
}

// 3. VU STAGE (Executed repeatedly by each VU in parallel)
export default function (data) {
    http.get('https://quickpizza.grafana.com');
    sleep(1);
}

// 4. TEARDOWN STAGE (Runs ONCE after all VUs terminate)
export function teardown(data) {
    console.log("=== Teardown: Cleaning up test data for ID:", data.testId);
}
```

### Core Takeaways
1. `setup()` and `teardown()` run in separate isolated environments, outside the VU iterations.
2. Never put login/auth in `default function` if you only need a single session token; put it in `setup()` to save unnecessary load on your authentication service.
3. Data returned from `setup()` is passed read-only to `default(data)` and `teardown(data)`.

# 📋 Complete k6 Cheat Sheet & Advanced SDET Reference

## 1. 📊 k6 Built-in Metrics Glossary

| Metric | Type | Meaning in Plain English | Healthy Target Value |
|---|---|---|---|
| `http_reqs` | Counter | Total count of HTTP requests generated by k6 across the entire test run. | Monotonically increasing; should equal or exceed target RPS × duration without flatlining. |
| `http_req_duration` | Trend | Total round-trip time for HTTP requests (sending + waiting for TTFB + receiving). | p(95) < 500ms and p(99) < 1000ms for web APIs; flat curve without steep degradations. |
| `http_req_failed` | Rate | Percentage of total HTTP requests resulting in HTTP 4xx/5xx status codes or network timeouts. | 0.00% ideal; strictly < 0.1% under normal load, < 1.0% under peak stress testing. |
| `http_req_waiting` | Trend | Time spent waiting for the target server to process and send the first byte (TTFB). | < 200ms; spikes indicate database query locks, CPU throttling, or heavy backend compute. |
| `http_req_connecting` | Trend | Time spent establishing the TCP connection between the k6 load engine and the server. | < 50ms (or ~0ms with HTTP Keep-Alive connection reuse); spikes show network saturation. |
| `iterations` | Counter | Aggregate count of times all Virtual Users completed executing the exported default function. | Matches target test plan; should scale linearly with active VUs if response time stays stable. |
| `iteration_duration` | Trend | Total time taken by a single VU to run one iteration (sum of all API calls + sleep think times). | Stable throughout steady-state; should closely match (API duration sum + sleep pacing). |
| `vus` | Gauge | Number of active concurrent Virtual User threads generating traffic at any specific second. | Smoothly tracks configured ramp-up, steady, and ramp-down stages without unexpected stalls. |
| `vus_max` | Gauge | Maximum pool of Virtual User threads provisioned in runner memory for the execution. | Equals peak VU target specified in options; confirms runner allocated adequate capacity. |
| `checks` | Rate | Cumulative success percentage of all check() assertions evaluated during the run. | ≥ 99.00% to 100%; any drop reveals unexpected response payloads or validation failures. |
| `data_sent` | Counter | Total volume of outbound network traffic payload bytes sent by k6 to the target server. | Consistent with request payload size multiplied by total request count. |
| `data_received` | Counter | Total volume of inbound network traffic payload bytes received back by k6 from the server. | Proportional to response body size; sudden drops under load indicate truncated 502/504 errors. |

## 2. ⚙️ Executors & Scenarios Guide

### `constant-vus` (Closed Workload)
* **Summary:** A fixed number of VUs execute iterations for a specified duration.
* **When to use:** Quick baseline benchmarks, local sanity checks, and fixed-concurrency smoke tests.

### `ramping-vus` (Closed Workload)
* **Summary:** A variable number of VUs ramp up, sustain, and ramp down across configured time stages.
* **When to use:** Load tests, stress tests, and peak traffic simulations allowing caches to warm up naturally.

### `constant-arrival-rate` (Open Workload)
* **Summary:** A fixed number of iterations start per time unit, dynamically allocating VUs to maintain exact RPS.
* **When to use:** Strict throughput/RPS testing where target request volume must not slow down when the server slows down (prevents Coordinated Omission).

### `ramping-arrival-rate` (Open Workload)
* **Summary:** Target iterations per time unit ramp up and down over stages, maintaining deterministic RPS.
* **When to use:** Testing autoscaling cloud systems, microservice rate-limiters, and ingress API gateway throttling.

### `per-vu-iterations` (Closed Workload)
* **Summary:** Each individual VU executes an exact, dedicated number of iterations before terminating.
* **When to use:** Processing fixed datasets (e.g. 50 VUs each processing 20 customer records in parallel) and migration tests.

### `shared-iterations` (Closed Workload)
* **Summary:** A fixed global pool of iterations is completed collectively by a pool of VUs as fast as possible.
* **When to use:** Batch job testing, processing a fixed queue of 5,000 orders across available parallel workers.

### Working Multi-Scenario Example (`orders-api`)
```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

// Multi-scenario configuration simulating concurrent traffic patterns
export const options = {
  scenarios: {
    // Scenario 1: Sustained background browsing (Open Workload: guaranteed 25 RPS)
    catalog_browsing: {
      executor: 'constant-arrival-rate',
      rate: 25,
      timeUnit: '1s',
      duration: '2m',
      preAllocatedVUs: 20,
      maxVUs: 50,
      exec: 'browseCatalog',
    },
    // Scenario 2: Peak checkout surge (Closed Workload: ramping concurrent buyers)
    checkout_surge: {
      executor: 'ramping-vus',
      startVUs: 0,
      stages: [
        { duration: '30s', target: 15 }, // Warm up
        { duration: '1m', target: 30 },  // Peak rush
        { duration: '30s', target: 0 },  // Ramp down
      ],
      gracefulRampDown: '10s',
      exec: 'placeOrder',
    },
  },
  thresholds: {
    'http_req_duration{scenario:catalog_browsing}': ['p(95)<300'],
    'http_req_duration{scenario:checkout_surge}': ['p(95)<700'],
    'http_req_failed': ['rate<0.01'],
  },
};

export function browseCatalog() {
  const res = http.get('https://orders-api.company.internal/api/v1/catalog?category=electronics');
  check(res, {
    'catalog loaded 200': (r) => r.status === 200,
  });
  sleep(0.5);
}

export function placeOrder() {
  const payload = JSON.stringify({
    customerEmail: 'priya.sharma@enterprise-retail.com',
    sku: 'LOGI-MX-MASTER-3S',
    quantity: 1,
    shippingAddress: { city: 'Bengaluru', pincode: '560001' },
  });

  const res = http.post('https://orders-api.company.internal/api/v1/orders', payload, {
    headers: { 'Content-Type': 'application/json' },
  });

  check(res, {
    'order created 201': (r) => r.status === 201,
    'has orderId': (r) => r.json().orderId !== undefined,
  });

  sleep(1);
}
```

## 3. 📈 Custom Metrics (Counter, Gauge, Rate, Trend)

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';
import { Counter, Gauge, Rate, Trend } from 'k6/metrics';

// 1. Counter: Tracks cumulative counts (always increases)
const ordersSubmittedCount = new Counter('orders_submitted_total');

// 2. Gauge: Tracks the current instantaneous value (can go up or down)
const cartItemCountGauge = new Gauge('current_cart_items_gauge');

// 3. Rate: Tracks the proportion of events matching a condition (0 to 1)
const paymentSuccessRate = new Rate('payment_success_rate');

// 4. Trend: Calculates min, max, avg, med, p(90), p(95), p(99) on custom timings
const paymentGatewayLatency = new Trend('payment_gateway_latency_ms');

export const options = {
  vus: 10,
  duration: '30s',
  thresholds: {
    'orders_submitted_total': ['count>50'],
    'payment_success_rate': ['rate>0.98'], // 98% payment success
    'payment_gateway_latency_ms': ['p(95)<450'], // 95% payments under 450ms
  },
};

export default function () {
  const orderPayload = JSON.stringify({
    customer: 'rahul.verma@enterprise-retail.com',
    items: [{ sku: 'KEYCHRON-K2-V2', price: 89.99, qty: 1 }],
  });

  // Track instantaneous cart item size
  cartItemCountGauge.add(1);

  const startTime = Date.now();
  const res = http.post('https://orders-api.company.internal/api/v1/orders', orderPayload, {
    headers: { 'Content-Type': 'application/json' },
  });
  const latency = Date.now() - startTime;

  const passed = check(res, {
    'order processed': (r) => r.status === 201,
  });

  if (passed) {
    ordersSubmittedCount.add(1);
    paymentSuccessRate.add(1); // 1 = Success
    paymentGatewayLatency.add(latency);
  } else {
    paymentSuccessRate.add(0); // 0 = Failure
  }

  sleep(1);
}
```

## 4. 🏷️ Organizing Results with Groups & Tags

```javascript
import http from 'k6/http';
import { group, check, sleep } from 'k6';

export const options = {
  vus: 5,
  duration: '30s',
  thresholds: {
    // Threshold scoped to a specific business transaction group
    'group_duration{group:::01_Customer_Search}': ['p(95)<400'],
    'group_duration{group:::02_Checkout_Transaction}': ['p(95)<800'],
    // Threshold scoped to tagged microservice requests
    'http_req_duration{service:inventory-service}': ['p(95)<250'],
    'http_req_duration{service:orders-api}': ['p(95)<500'],
  },
};

export default function () {
  // Group 1: Search & Browse
  group('01_Customer_Search', function () {
    const searchRes = http.get(
      'https://inventory-service.company.internal/api/v1/search?query=keyboard',
      { tags: { service: 'inventory-service', endpoint: 'search' } }
    );
    check(searchRes, { 'search ok': (r) => r.status === 200 }, { check_type: 'search' });
    sleep(1);
  });

  // Group 2: Order Creation & Checkout
  group('02_Checkout_Transaction', function () {
    const payload = JSON.stringify({
      user: 'priya.sharma@enterprise-retail.com',
      item: 'LOGI-MX3S',
      amount: 99.0,
    });

    const orderRes = http.post(
      'https://orders-api.company.internal/api/v1/orders',
      payload,
      {
        headers: { 'Content-Type': 'application/json' },
        tags: { service: 'orders-api', endpoint: 'create_order' },
      }
    );

    check(orderRes, { 'order created': (r) => r.status === 201 }, { check_type: 'create_order' });
    sleep(1.5);
  });
}
```

## 5. 🗂️ Data Parameterization with SharedArray

> **Why NEVER read files inside `default()`:** Every VU repeats file parsing on every iteration, leading to rapid Out-of-Memory (OOM) crashes. `SharedArray` reads and parses once in the init phase into shared read-only memory.

```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';
import { SharedArray } from 'k6/data';

/**
 * CRITICAL PERFORMANCE PRINCIPLE:
 * Why NOT to read or parse files inside the default function:
 * - If you use JSON.parse() or open() inside export default function(),
 *   every single VU will read from disk and re-parse the file on EVERY loop.
 * - With 100 VUs and 1,000 iterations, a 5MB dataset gets loaded 100,000 times,
 *   causing Out-Of-Memory (OOM) crashes and consuming 100% test machine CPU.
 * 
 * SharedArray reads and parses the dataset ONCE in the init context (memory shared across all VUs),
 * keeping memory footprint virtually zero regardless of VU count.
 */

// Initialize SharedArray once (Read-only shared memory)
const customerAccounts = new SharedArray('Customer Test Accounts', function () {
  // In production: return JSON.parse(open('./data/customers.json'));
  // Or parse CSV via papaparse. Here is a realistic parsed dataset:
  return [
    { email: 'priya.sharma@enterprise-retail.com', customerTier: 'PLATINUM', quota: 50 },
    { email: 'rahul.verma@enterprise-retail.com', customerTier: 'GOLD', quota: 30 },
    { email: 'ananya.iyer@enterprise-retail.com', customerTier: 'SILVER', quota: 15 },
    { email: 'vikram.singh@enterprise-retail.com', customerTier: 'BRONZE', quota: 10 },
  ];
});

export const options = {
  vus: 4,
  duration: '20s',
};

export default function () {
  // Deterministically assign unique account per VU using __VU index
  const accountIndex = (__VU - 1) % customerAccounts.length;
  const user = customerAccounts[accountIndex];

  const payload = JSON.stringify({
    accountEmail: user.email,
    tier: user.customerTier,
    orderTimestamp: new Date().toISOString(),
  });

  const res = http.post('https://orders-api.company.internal/api/v1/orders', payload, {
    headers: { 'Content-Type': 'application/json' },
  });

  check(res, {
    'order accepted': (r) => r.status === 201,
  });

  sleep(1);
}
```

## 8. ⚠️ Top 10 Common Beginner Mistakes & Fixes

### 1. Authenticating Inside the default() Function on Every Loop
* **Symptom:** Auth service crashes or returns HTTP 429 Too Many Requests within 5 seconds.
* **Problem:** Every VU repeats the /auth POST on every single loop, generating millions of redundant logins and creating a false bottleneck.
* **Fix:** Authenticate ONCE inside export function setup(). Return the token and let export default function(data) receive it read-only in data.token.

### 2. Reading or Parsing Files Inside the default() Function
* **Symptom:** High CPU on test machine, high GC pauses, or sudden Out-Of-Memory (OOM) crash.
* **Problem:** open() or JSON.parse() executed per-iteration causes repeated file I/O and memory explosion.
* **Fix:** Use SharedArray from k6/data in the init context to load data once into shared read-only memory.

### 3. Omitting sleep() (Zero Think Time)
* **Symptom:** Unrealistic hammering; 10 VUs generate 5,000 RPS and drown the server.
* **Problem:** Real humans pause between page clicks (think time). Zero sleep makes a small VU count behave like a DDoS attack.
* **Fix:** Add realistic pauses: sleep(1) or random pacing: sleep(Math.random() * 2 + 1).

### 4. Expecting check() to Halt the Test or Fail CI Pipelines
* **Symptom:** All checks fail with 0% pass rate in the summary, but GitHub Actions still passes with a green checkmark.
* **Problem:** checks are non-blocking diagnostic assertions; they never stop execution and never return an error exit code.
* **Fix:** Define thresholds in options (e.g. checks: ['rate>0.99']). Threshold failures cause k6 to exit with code 99.

### 5. Confusing VUs (Virtual Users) with TPS / RPS (Throughput)
* **Symptom:** Targeting 500 RPS by setting vus: 500, but requests fluctuate unpredictably.
* **Problem:** With closed workloads, RPS is governed by server response time + sleep pacing: RPS = VUs / (ResponseTime + ThinkTime). When the server slows down, RPS drops.
* **Fix:** Use the constant-arrival-rate executor when strict RPS target benchmarking is required.

### 6. Hardcoding Dynamic Correlation Tokens Between Requests
* **Symptom:** HTTP 400 Bad Request or HTTP 404 Not Found on checkout and booking endpoints.
* **Problem:** Reusing static IDs or session tokens across parallel VUs causes duplicate key conflicts or expired session errors.
* **Fix:** Extract dynamic IDs from previous responses via res.json().orderId and pass them into subsequent requests.

### 7. Importing Node.js or Standard npm Packages Directly
* **Symptom:** ModuleNotFoundError or syntax errors like require() is not defined.
* **Problem:** k6 is built on an embedded Goja JS engine, not Node.js. It does not support Node core modules (fs, path, crypto) or arbitrary npm packages.
* **Fix:** Use native k6 modules (k6/http, k6/data, k6/crypto) or official https://jslib.k6.io/ browser-compatible bundles.

### 8. Jumping Instantly to Maximum Load Without Ramp-Up Stages
* **Symptom:** Immediate HTTP 502/504 Bad Gateway errors at second 1 of the test run.
* **Problem:** Instant concurrency overwhelms cold database connection pools, cold JIT compilers, and unprimed caches.
* **Fix:** Always configure stages with a 1–3 minute ramp-up stage to let the infrastructure warm up gracefully.

### 9. Not Using Tags or Groups to Isolate Microservice Latencies
* **Symptom:** The summary reports http_req_duration p(95)=1200ms, but nobody knows which microservice endpoint caused the slowdown.
* **Problem:** k6 lumps all HTTP calls into a single aggregate metric by default.
* **Fix:** Add tags: { service: 'orders-api' } to requests or wrap endpoints in group() to get per-endpoint percentiles in the report.

### 10. Ignoring Test Runner Host OS Limits (Open Files / Sockets)
* **Symptom:** socket: too many open files or connection reset by peer errors originating from the runner machine.
* **Problem:** Default Linux ulimit restricts file descriptors to 1,024, blocking thousands of concurrent outbound TCP sockets.
* **Fix:** Run ulimit -n 65535 on Linux/Mac before running heavy tests, and ensure sysctl TCP socket reuse is enabled.

## 9. 🎯 15 SQA / SDET Interview Questions & Answers

### Q1: What is the fundamental architectural difference between Grafana k6 and Apache JMeter?
**Answer:** JMeter is Java-based, runs on a heavyweight JVM, uses thread-per-VU model, and relies on XML GUI test plans, requiring high memory (often 4GB+). k6 is written in Go, uses lightweight goroutines (1 VU takes ~20–40KB of memory), and executes tests written in standard modern JavaScript (ES6) CLI-first.

### Q2: What are k6 Thresholds, and what exit code does k6 return when an SLA is breached?
**Answer:** Thresholds are automated pass/fail quality criteria defined on metrics (e.g. http_req_duration: ['p(95)<500'], http_req_failed: ['rate<0.01']). When any threshold breaches, k6 terminates with exit code 99 (instead of 0), signaling automated CI/CD pipelines (GitHub Actions, Jenkins) to fail the build.

### Q3: How does k6 achieve high concurrency without crashing runner memory?
**Answer:** k6 utilizes Go's goroutine scheduler rather than heavy OS threads. Each Virtual User is an isolated Goja JavaScript runtime instance sharing common memory constructs (like SharedArray). A single machine can comfortably generate 30,000+ VUs in k6 where JMeter would crash with OutOfMemoryError.

### Q4: Explain the 4 stages of the k6 test execution lifecycle.
**Answer:** 1) Init Stage: imports modules and loads SharedArray once. 2) Setup Stage: export function setup() runs once before VUs to authenticate or seed data. 3) VU Stage: export default function(data) runs repeatedly across parallel VUs. 4) Teardown Stage: export function teardown(data) runs once after all VUs terminate for cleanup.

### Q5: What is the difference between a check() and a threshold in k6?
**Answer:** A check() is a non-blocking diagnostic assertion (like verifying HTTP 200 or JSON body keys) that records a pass/fail rate in the summary without halting the test. A threshold is an enforceable SLA rule; if a threshold (e.g. checks: ['rate>0.99']) fails, k6 exits with code 99 to fail CI/CD.

### Q6: Why should you avoid placing authentication calls inside the default() function?
**Answer:** Placing auth inside default() causes every VU to call /auth on every loop, generating thousands of logins per second. This creates an artificial bottleneck on the auth service and obscures the performance of the actual business endpoints being tested. Auth belongs in setup().

### Q7: How do you safely parameterize test data across thousands of concurrent VUs in k6?
**Answer:** Use SharedArray from the k6/data module. It reads and parses JSON/CSV data once in the init stage and shares it read-only in memory across all VUs, preventing high memory usage and garbage collection pauses. Indexing is mapped with __VU and __ITER.

### Q8: What is the difference between constant-vus and constant-arrival-rate executors?
**Answer:** constant-vus is a closed model where a fixed number of VUs loop; if the server responds slowly, throughput drops. constant-arrival-rate is an open model that dynamically spins up VUs to guarantee an exact target iteration/request rate per second regardless of how slow the server becomes.

### Q9: What is Coordinated Omission in load testing, and how does k6 combat it?
**Answer:** Coordinated Omission occurs when a slow server delays the test runner from issuing subsequent scheduled requests, concealing high latency from final metrics. k6 combats this via arrival-rate executors (constant-arrival-rate), which schedule requests at independent fixed timestamps.

### Q10: How do you pass dynamic runtime variables from CI/CD into a k6 script without editing code?
**Answer:** Use the CLI flag -e KEY=VALUE (e.g., k6 run -e BASE_URL="https://staging.api.com" -e TARGET_VUS=50 script.js) and access them inside the JavaScript code via __ENV.BASE_URL and Number(__ENV.TARGET_VUS).

### Q11: How do you organize transactions and isolate metrics for individual microservices in k6?
**Answer:** Use group('Transaction_Name', () => { ... }) for logical business step boundaries, and attach tags: { service: 'orders-api' } to requests. You can then write targeted thresholds such as 'http_req_duration{service:orders-api}': ['p(95)<300'].

### Q12: What are Custom Metrics in k6, and when would you use a Trend vs a Rate?
**Answer:** k6 provides 4 custom metric types: Counter (cumulative counts), Gauge (instantaneous values), Rate (percentage of booleans matching true), and Trend (statistical metrics like p90/p95). Use Rate for business success ratios and Trend for custom operational timings (e.g. payment gateway processing time).

### Q13: How does k6 handle cookies and session headers across sequential requests?
**Answer:** k6 automatically manages an isolated cookie jar per Virtual User, replicating realistic browser cookie persistence for each VU session. You can also manually inspect and set cookies via http.cookieJar().

### Q14: Can k6 perform frontend browser performance testing alongside API protocol testing?
**Answer:** Yes! Using the official k6/browser module (formerly xk6-browser), k6 can launch headless Chromium instances to measure real browser rendering metrics, Core Web Vitals (LCP, FID, CLS), and DOM interactions simultaneously with API load.

### Q15: How do you view live interactive visual dashboards and export static HTML reports from k6?
**Answer:** Set K6_WEB_DASHBOARD=true when running k6 to open a live real-time dashboard at http://localhost:5665. To export a shareable standalone HTML report for stakeholders or CI artifacts, run K6_WEB_DASHBOARD=true K6_WEB_DASHBOARD_EXPORT=report.html k6 run script.js.

## 11. 📊 Real-Time Monitoring with Grafana + InfluxDB 1.8

### What each tool does in plain English:
* **k6 (Load Generator):** Executes test iterations across concurrent VUs and continuously streams live HTTP metric points.
* **InfluxDB 1.8 (Time-Series Store):** Ingests and stores raw metrics in real time inside the `k6` database on port 8086.
* **Grafana (Visualization UI):** Queries InfluxDB on port 3000 to render interactive latency, RPS, and VU graphs as the test runs.

### docker-compose.yml
```yaml
version: '3.8'

services:
  influxdb:
    image: influxdb:1.8
    container_name: k6-influxdb
    ports:
      - "8086:8086"
    environment:
      - INFLUXDB_DB=k6
    volumes:
      - influxdb_data:/var/lib/influxdb

  grafana:
    image: grafana/grafana:latest
    container_name: k6-grafana
    ports:
      - "3000:3000"
    environment:
      - GF_AUTH_ANONYMOUS_ORG_ROLE=Admin
      - GF_AUTH_ANONYMOUS_ENABLED=true
      - GF_AUTH_BASIC_ENABLED=false
    volumes:
      - grafana_data:/var/lib/grafana
    depends_on:
      - influxdb

volumes:
  influxdb_data:
  grafana_data:
```

### Execution Command
```bash
k6 run --out influxdb=http://localhost:8086/k6 script.js
```

### How to Configure InfluxDB in Grafana:
1. Open **http://localhost:3000** in your browser.
2. Go to **Connections / Data Sources** -> **Add data source** -> select **InfluxDB** (Query language: **InfluxQL**).
3. Set HTTP URL to `http://influxdb:8086` (or `http://localhost:8086` if not in Docker).
4. Under Database, type `k6` and click **Save & test**.

### How to Import Ready k6 Dashboard (ID 2587):
1. In Grafana, click **Dashboards** -> **New** -> **Import**.
2. Enter Dashboard ID **2587** (official Grafana community k6 dashboard) and click **Load**.
3. Choose your InfluxDB data source and click **Import**.

> **Modern Alternative Note:** In modern cloud-native Kubernetes environments, Grafana recommends the **Prometheus remote-write output** (`k6 run -o experimental-prometheus-rw=http://localhost:9090/api/v1/write script.js`) to stream directly to Prometheus or Grafana Mimir.

## 12. 🔧 Passing Values with Environment Variables

Execute via CLI flag:
```bash

```

### Script Code Reading `__ENV` with Fallback Defaults:
```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

/**
 * Reading environment variables in k6:
 * Access variables passed via CLI using __ENV.<VARIABLE_NAME>
 * Always provide a safe fallback value with the logical OR (||) operator.
 */
const BASE_URL = __ENV.BASE_URL || 'https://orders-api.company.internal';
const TARGET_VUS = Number(__ENV.TARGET_VUS) || 10;
const AUTH_TOKEN = __ENV.AUTH_TOKEN || 'dev-fallback-token-secret-99';

export const options = {
  vus: TARGET_VUS,
  duration: '30s',
  thresholds: {
    http_req_duration: ['p(95)<450'],
    http_req_failed: ['rate<0.01'],
  },
};

export default function () {
  const payload = JSON.stringify({
    customerEmail: 'priya.sharma@enterprise-retail.com',
    sku: 'LOGI-MX-MASTER-3S',
    orderChannel: 'MOBILE_APP',
  });

  const headers = {
    'Content-Type': 'application/json',
    'Authorization': `Bearer ${AUTH_TOKEN}`,
  };

  const res = http.post(`${BASE_URL}/api/v1/orders`, payload, { headers });

  check(res, {
    'order accepted 201': (r) => r.status === 201,
    'has valid orderId': (r) => r.json().orderId !== undefined,
  });

  sleep(1);
}
```
